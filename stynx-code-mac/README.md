# Stynx Desktop (macOS)

Native SwiftUI front-end for the stynx engine. The Rust core is compiled into a
static library and called in-process through [uniffi](https://github.com/mozilla/uniffi-rs)
bindings — one process, one binary, no sidecar.

```
SwiftUI app ──uniffi──▶ libstynx_code_ffi.a  (stynx-code-ffi → stynx-code-app → engine)
```

## Layout

- `stynx-code-app/` — shared application assembly (provider resolution, tool
  registry, system prompt, engine wiring). Consumed by both the TUI binary and
  the FFI crate, so there is one source of truth.
- `stynx-code-ffi/` — uniffi crate. Exposes `StynxSession` + an `EventListener`
  callback interface mirroring the engine's `EngineEvent` stream.
- `stynx-code-mac/Sources/` — SwiftUI app, layered like the Rust workspace:
  - `Domain/` — pure models and logic (feed items, diff engine, markdown/QA
    parsing, permission modes); no AppKit, no FFI.
  - `Application/` — view models (`SessionViewModel` + extensions, `AppModel`)
    orchestrating the FFI session and app state.
  - `Infrastructure/` — adapters to the outside world: FFI event listener,
    reference store/extractor (disk, PDFKit, HTTP), pasteboard.
  - `Presentation/` — SwiftUI views and the app entry point.
- `stynx-code-mac/Generated/` — uniffi-generated Swift bindings (regenerated by the build).
- `stynx-code-mac/Frameworks/StynxCoreFFI.xcframework` — packaged static lib + headers.

## Build

Two steps, because the Rust build needs the Nix devshell environment while
`xcodebuild` needs a clean environment (the Nix shell exports `DEVELOPER_DIR`,
`SDKROOT`, `LD`, `CC` which otherwise hijack Apple's toolchain and break linking).

```bash
# 1. Build the Rust static lib, generate Swift bindings, assemble the xcframework
#    (run inside the nix devshell — needs openssl/rust toolchain)
./stynx-code-mac/scripts/build-rust.sh

# 2. Build the SwiftUI app (strips the environment down to essentials internally)
./stynx-code-mac/scripts/build-app.sh
```

The app lands at `stynx-code-mac/build/Build/Products/Debug/Stynx.app`.

## Credentials

The engine resolves credentials exactly like the TUI: `ANTHROPIC_API_KEY`,
Claude OAuth (`~/.claude/.credentials.json`), or an OpenAI-compatible intern
provider key (`DEEPSEEK_API_KEY`, `QWEN_API_KEY`, `OPENROUTER_API_KEY`, …). With
no credential configured the session reports `init failed: No credentials found`.

## Status

- Streaming chat + tool-call rendering through the Rust↔Swift pipe.
- Permission approval flow: the engine's `PromptBridge` and `ask_user`
  `QuestionBridge` are installed on the FFI side; requests surface as
  `permissionRequest` / `askUserRequest` events and resolve through
  `respondPermission` / `respondAskUser`. The app runs in `Normal` mode and
  shows native approval sheets.

Not yet wired: sessions list, model picker, intern panel, themes, command
palette — see the parity backlog in the project plan.

## Distribution note

Full bash + arbitrary-filesystem tool access is incompatible with the App Store
sandbox. This ships as a notarized DMG (Hardened Runtime, sandbox off), not via
the Mac App Store.
